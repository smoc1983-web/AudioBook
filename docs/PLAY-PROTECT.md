# Play Protect installation report (2026-10-26)

The supplied screenshot matches Google's “App blocked to protect your device” / sensitive-data warning. It is distinct from an APK download failure or signing mismatch. Google documents enhanced protection for internet-sideloaded packages with certain sensitive APIs: https://developers.google.com/android/play-protect/warning-dev-guidance . The screenshot alone does not provide Google's complete verdict or prove which individual API caused it.

The 4.2.62 manifest declared an AccessibilityService for opt-in legacy collection screen reading. It also included Shizuku for a separate old-debug-app migration path. Neither is needed for audio playback, local library access, ordinary notifications or user-selected backup import. These paths are removed from the installable application, not renamed, hidden behind switches or moved to an automatically installed helper. Their historical sources and tests are retained under history/privileged-collection-transfer-4.2.62, outside every app source set.

The replacement keeps only JSON/XML import/export, preview before confirmation, additive merge, backup before import and undo. Existing shelves/preferences and library paths are unchanged. A legacy app without export cannot have its private collections read automatically by the new application; users can select an existing backup or rebuild shelves manually. No Android protection settings need to be disabled for this workflow.

The user-facing APK is now a non-debuggable release, signed with the SAME existing certificate and applicationId. This is packaging hardening, not an assertion that debugging alone caused the warning. Release and debug test APKs share the existing CI signing identity so an actual baseline->release data-preservation test can run. The old updater must verify the signed release and open Android's update confirmation; after replacement the test checks preferences, shelves, selected library URI, a private control file, a valid WAV checksum, absence of the retired components and successful release-home startup.

The publication gate audits the actual installable APK: reviewed media/update permissions only, no accessibility/notification-listener/SMS bindings, no Shizuku and no retired privileged class definitions in DEX. Tests fail closed for a debug APK, unknown permission, sensitive service or retained implementation. This is a local permission/build audit, not a Google malware review or an acceptance verdict.

Google Play Protect acceptance cannot be established with an AOSP emulator without Play services. If a revised package remains blocked on the affected devices, the developer must use Google's official Play Protect appeal/review process with the actual new APK, package, certificate and screenshot. The correction does not change the certificate/package to evade an existing classification and does not instruct users to disable Play Protect. Any appeal remains a separate external submission; no appeal has been filed by this automation.
